# Decision-Making Strategy

本文档记录当前后端已经实现的对话决策策略，重点说明问询顺序、`scene` 多地点收敛、非旅行意图拦截，以及最终 inspiration 的生成约束。

## 1. 当前目标

当前策略的核心目标有四个：

1. 单个 `inspiration` 只围绕一个核心地点或高度连贯区域展开。
2. 当输入可高置信度联想到多个地点时，不直接生成，而是先进入 `scene` 澄清。
3. 问询顺序不再固定为 `mood -> scene -> focus`，而是按阻塞条件动态调整。
4. 纯文学解释、书单推荐、明确否定旅行意图的输入，不进入旅行灵感链路。

## 2. 三个结构化字段

当前系统仍围绕三个 requirement 字段工作：

- `mood`：情感基调、气质、氛围
- `scene`：旅行发生的地点、区域、空间环境
- `focus`：旅行中的行动、体验、感官关注点

生成最终 inspiration 前，会先尝试从用户输入中抽取并评分这三个字段。

## 3. 问询顺序策略

### 3.1 动态顺序，而非固定顺序

当前实现已从固定顺序切换为“阻塞条件优先 + 常规补全兜底”。

决策顺序如下：

1. 如果 `scene` 存在多个高置信度地点候选，优先问 `scene`
2. 否则，如果 `focus` 已经较强，而 `scene` 很弱、`mood` 也未成形，则优先问 `focus`
3. 如果没有明显阻塞条件，再按未达标字段中的最低分继续追问

### 3.2 为什么 `scene` 多地点时优先问 `scene`

因为这类情况不是普通的信息不足，而是“关键分叉未消解”：

- 不先定地点，最终文案容易漂移
- 模型容易替用户擅自选择地点
- 后续 `focus`/`mood` 的补全可能失真
- 最终容易生成并列的多个分散地点

所以当 `scene` 有多个候选时，系统会把它视为一个阻塞条件，而不是普通低分字段。

### 3.3 为什么某些情况下优先问 `focus`

有些 query 是明显的“行为主导型输入”，例如：

- 想边走边写作
- 想住十来天慢慢待着
- 想散步、看旧书店、找作家故居

这类输入里，用户往往先确定旅行方式，再决定地点。  
因此当 `focus` 已经足够强、`scene` 尚弱且没有多地点冲突时，系统会优先追问 `focus`，用行为约束帮助地点收敛。

## 4. Scene 多地点收敛策略

### 4.1 内部状态

当前 `scene` 支持内部多地点候选状态：

- 若只提取到一个高置信度地点，写入 `scene.content`
- 若提取到多个高置信度地点：
  - 不直接写入最终 `scene.content`
  - 内部保存到 `SceneCandidates`
  - `scene.score` 保持未达标
  - 阻止直接生成 inspiration

这个候选状态只在后端内部使用，不通过公开 API 暴露。

### 4.2 澄清问题生成方式

当 `scene` 存在多个候选时：

- `target_field` 仍然是 `scene`
- 对外仍返回普通的 `clarify_question`
- `options` 直接取自已提取出的地点候选
- 不再让模型重新自由发挥 scene 选项

用户选择某个地点后：

- 该地点写回 `scene.content`
- 候选列表清空
- `scene` 进入已满足状态

### 4.3 Scene 选项纯度要求

当前策略要求 `scene` 的 options 必须是纯地点或高度连贯区域，不能混入：

- 情绪词
- 动作
- 节奏描述
- 美食或体验项目
- 文学主题本身

例如，应优先输出：

- `东京神保町`
- `北海道小樽`
- `神户旧居留地`

而不是：

- `充满历史感的古城老街与慢生活节奏`

## 5. 最终生成约束

当前 inspiration 生成 prompt 已加入以下约束：

- 整篇只围绕一个核心地点或一个高度连贯区域展开
- 不并列推荐多个分散地点
- 地点必须尽量精确到城市区域、县镇、街区、村庄或明确地貌带

这意味着只要 `scene` 还没收敛，系统就不会进入最终生成阶段。

## 6. 作家 / 作品相关输入的增强

对于作家、作品、文学人物强相关的 query，系统当前已加强最终文案的约束，要求在地点收敛后尽量补充：

- 哪位作家或作品与此地有关
- 曾在此发生过什么
- 哪些旧居、书店、港口、街区、路径仍能承接这种联系

目标不是堆文学典故，而是把文学关联落到可抵达、可观察、可停留的空间细节上。

## 7. 非旅行意图拦截

当前 `intent` 识别已从宽松口径收紧，以下输入会被优先判定为非旅行：

- 明确否定旅行意图  
  例如：`我不想旅游，我只是想找几本关于西南边地书写的书`
- 纯文学概念解释  
  例如：`请解释一下物哀是什么意思`
- 纯书单 / 荐书 / 作品讨论  
  例如：`推荐几本关于边地书写的书`

对这类输入，系统不会进入旅行灵感生成链路，而会返回更明确的提示，告诉用户如果想转成旅行方向，需要补充：

- 想去体验的地点
- 想要的旅行场景
- 希望在旅行中做的事情

## 8. 对外接口变化

本轮策略调整未改动公开 API 结构：

- 仍使用 `clarify_question`
- `target_field` 仍为 `mood | scene | focus`
- `options` 仍为字符串选项
- 未新增新的消息类型

新增的 `scene` 多候选状态仅存在于后端内部。

## 9. 当前已实现的判定要点

当前代码已经实现以下规则：

- `scene` 多候选未收敛时，不允许生成最终 inspiration
- `scene` 多候选时，下一问强制优先 `scene`
- `focus` 已较强、且 `scene/mood` 仍弱时，可优先问 `focus`
- `scene` 澄清优先使用内部候选地点，而不是重新让 LLM自由生成
- 最终 inspiration 强制单地点
- 纯文学解释 / 书单 / 明确非旅行输入会被拦截

## 10. 后续建议

虽然当前版本已经解决了最主要的问题，但仍建议继续迭代以下方向：

1. 为更多作家 / 作品建立更稳定的高置信度地点映射
2. 进一步细化“行为主导型输入”的识别规则
3. 为 `mood/scene/focus` 的 option 纯度增加更多测试集
4. 建立一套固定评估集，对 query、clarify question、options 和最终 inspiration 做回归对比
